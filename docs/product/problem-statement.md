# 问题陈述

## 为谁

优先级 cascade：

1. **Agent Builder** — 定义、扩展、发布自己的 agent 团队
2. **小团队** — 共享同一套团队规范、进度与质量门禁
3. **单人** — 开箱默认团队，不必先成为 builder

## 我在做什么

用 AI agent 完成真实工程与产品工作（编码、调研、规格、质量、推进），且希望是**一支协作团队**，而非一个「超强单体助手」。

## 但

| 痛点 | 说明 |
|------|------|
| **单体优先** | 「AI 员工」类产品默认一个很强个体，团队协作不是一等公民 |
| **Harness 绑定** | 团队工作流嵌在某一 IDE 或 runtime 里，难以迁移 |
| **流程要么过重要么过轻** | 全文档门禁拖死探索；纯敏捷缺少 DDD 与质量下限 |
| **无通用编制规则** | 要么固定角色表，要么完全自由，缺少「可加减槽位」的协议 |
| **非编码能力割裂** | 调研、竞品、PRD 与编码交付不在同一套团队协议里 |

## 因为

- Harness（Cursor、CLI、OpenHands 等）会不断变化，**不应把团队定义写死在某一运行时**
- **DDD 领域模型驱动**是复杂任务的质量底座，不能靠「多聊几轮」替代
- 不同任务风险不同，需要**可调节的流程重量**，而非永远同一套 ceremony

## 这让我感到

- 重复搭建团队与工作流，每个项目从零配 agent
- 不敢让多 agent 并行，怕打架、怕幻觉交付、怕进度失控
- 好实践散落在 Voyage、青蚨使、agent-skills 里，**缺一个可开源、可组队的框架**

---

## 扶摇 · Nomad 要做什么

开源 **Agent 团队框架**：

- **团队优先** — 多角色协作、推进、管理、质量为一等公民
- **DDD 必要** — 领域模型驱动设计是交付底座
- **编制规则** — 通用槽位加减协议，无固定「官方编制」
- **轻-重流程重量** — 从青蚨使/Voyage 择优组合，按情境调节
- **薄适配挂载** — 挂到现有 harness，**不做、不替代 harness**

## 非目标

| 非目标 | 说明 |
|--------|------|
| ❌ 不做 harness | 不做 IDE、不做通用 agent runtime |
| ❌ 不做单体 AI 员工 | 不追求「一个 agent 干所有事」 |
| ❌ 不预设固定编制 | 不提供须维护的「标准八人团」 |
| ❌ 不照搬青蚨使/Voyage 全套 ceremony | 继承机制，调节重量（见 [delivery-model.md](delivery-model.md)） |
| ❌ 不以「敏捷」为主叙事 | 轻量手段按需用，主轴是 DDD + 情境化重量 |

## 成功时

- Builder 能定义槽位、绑技能、设门禁，发布可复用团队包
- 小团队在同一 roster 与 DoD 下协作，进度与质量可审计
- 单人用默认配置即可推进任务，并能随项目加重或减轻流程
- 换 harness 时，团队规格与交付协议无需重写
